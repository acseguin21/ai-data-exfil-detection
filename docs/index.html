Is your data leaving when you run open-weight models?

A shift-left way to tell whether a model you run with tool or code access is making unsolicited network calls — before it touches anything that matters.

The problem, in plain terms

Teams increasingly run open-weight models inside agent harnesses, evaluation pipelines, and tool-using RAG systems — contexts where the model can execute shell commands. In a published investigation, an open-weight model, given an ordinary security task, spontaneously issued curl commands that tried to send a probe payload to third-party cloud object storage and to a cloud metadata endpoint — without being asked. (documented by Cohere; the recorded destination was an Alibaba Cloud bucket in the Beijing region.)

Whether that behaviour is common, rare, or benign, the governance question is concrete: if a model-driven process in your environment reaches out, where does the data go? Cloud object storage and metadata endpoints are destinations you may not control, sometimes operated in other jurisdictions — a data-residency and exfiltration-surface concern regardless of intent.

What this is, and isn't. This is defensive detection content so responders can see for themselves whether it happens in their own setup. It is not an accusation about any model or vendor: the observed behaviour is probabilistic and not confirmed data theft. The point is visibility, not a verdict.

Who should look

  • Anyone running open-weight models with tool / code execution — agents, autonomous eval rollouts, CI that runs model-generated commands.
  • Security and incident-response teams who want a shift-left signal: catch egress in the eval pipeline before a model reaches production.
  • Platform teams who need to prove, for governance, that sandboxed model runs do not phone home.

Example 1 — check a model run for egress

Point the trace detector at an agent/eval rollout (your own logs, or a published trace). It flags any outbound call to a destination outside your sanctioned allowlist, and any cloud-metadata access:

$ python detections/agent_trace_detector.py rollout-trace.jsonl

[    HIGH] record 4: unsanctioned -> sanmaohe.oss-cn-beijing.aliyuncs.com
          (T1567.002; upload to a destination outside the sandbox allowlist)

[trace-detector] 1 finding(s) in rollout-trace.jsonl   # exit 2 -> fails your CI gate

Run against the published investigation trace, it surfaces the egress attempt at the point it was emitted — which is exactly where you'd want to catch it in your own pipeline.

Example 2 — prove it's signal, not noise

At an AI lab, curl to cloud storage runs constantly (weights, datasets, checkpoints). So the detections are allowlist-relative: they alert on what is not sanctioned, plus metadata access. The repo ships a benign ML-ops corpus to keep false positives honest:

$ python detections/validate.py

[validate] benign ML-ops commands : 10
[validate]   false positives       : 0   (target 0)
[validate] malicious commands      : 6
[validate]   true positives        : 6/6
[validate] precision on this corpus: 100.0%
[validate] PASS — zero false positives, all exfil caught.

Example 3 — deploy where it fits

Same logic, three places — pick what you already run:

Kubernetes runtimeFalco rules (detections/falco/) DaemonSet scoped to sandbox namespaces; pair with default-deny egress.
SIEMSigma → Splunk / Sentinel / Elastic Metadata rule turnkey; egress rule once you set your allowlist.

The Sigma rules pass sigma check and convert via pySigma; mapped to MITRE ATT&CK T1552.005 (cloud metadata) and T1567.002 (exfiltration to cloud storage).

Check your own usage

  1. Export an agent/eval rollout to JSONL (tool calls / executed commands).
  2. Edit detections/allowlist.json to your sanctioned destinations (your buckets and mirrors — scope to specific buckets, never a whole provider).
  3. python detections/agent_trace_detector.py your-rollout.jsonl
  4. Wire it into CI so a rollout that tries to egress fails the build.

The egress rules can watch for destinations under jurisdictions you care about (data-residency), and ship with a regression test (detections/validate.py) that keeps false positives at zero. See the repository README, detections/TESTING.md and DISCLAIMER.md.
